# Codex - Symlink Projection

Codex (OpenAI's CLI, `~/.codex/`) reads the same markdown formats as the config repo. Most artifacts propagate via symlinks. Commands are the exception: Codex has no user-command surface, so they're projected as skill wrappers instead.

## Layout Mapping

| Config repo source | Codex target | Strategy | Notes |
| ------------- | ------------ | -------- | ----- |
| `agents` | `~/.codex/agents` | dir symlink | Codex reads `.md` agents natively |
| `CLAUDE.md` | `~/.codex/AGENTS.md` | file symlink | Both are the top-level guidance file |
| Claude runtime memory | `~/.codex/memories` | dir symlink | Shared memory pool remains local runtime state |
| `skills/*` | `~/.codex/skills/*` | **per-child** symlink | Must preserve `.system/` |
| `commands/*` | `~/.codex/skills/cmd-<name>/SKILL.md` | `strategy_command_to_codex_skill` | Generates a Codex skill wrapper per command. Auto-loads when the user mentions the command name or related intent keywords. |
| `hooks/*` | `~/.codex/hooks/*` | **per-child** symlink | Hook scripts stay shared; symlinks keep them in lock-step without copying. |
| `settings.json` `hooks` key | `~/.codex/hooks.json` | `strategy_translate_hooks_to_codex_json` | Lifts the `hooks` block, rewrites `$HOME/.claude/hooks/` to `$HOME/.codex/hooks/`, and propagates hook changes automatically. |
| MCP source set | `~/.codex/config.toml` `[mcp_servers.*]` inside managed-block markers | `strategy_mcp_to_codex` | Uses selected MCP manifest plus Claude connector registry overlay; non-source servers outside the block are preserved. See [mcp-manifest.md](mcp-manifest.md). |

## The `.system/` Rule

**Never** make `~/.codex/skills` a single directory symlink. Codex manages its own system skills under `~/.codex/skills/.system/` (e.g., `imagegen`, `openai-docs`, `plugin-creator`, `skill-creator`, `skill-installer`) and re-writes them on startup, keyed by the marker file `.codex-system-skills.marker`.

If you symlink the whole dir:

1. Codex writes its `.system/` into the shared skills tree (pollutes the source)
2. Claude may or may not treat `.system/` as a skill (undefined behavior)
3. Syncthing propagates Codex's system skills to other machines (bloat)

The fix is `strategy_symlink_children(source=CONFIG_HOME / "skills", target=~/.codex/skills, preserve=[".system"])`:

- Links each skill individually under `~/.codex/skills/<name>`
- Leaves `.system/` untouched
- Prunes symlinks for skills that were removed from the repo `skills/`

## Detection Signature

```python
detect = lambda h: (h / "config.toml").exists() or (h / "AGENTS.md").exists()
```

The OR is intentional: `config.toml` is the modern signature; `AGENTS.md` is the fallback for installs that predate it. Both are Codex-owned (the `AGENTS.md` fallback is only valid before the sync engine symlinks it - which is why we also require the home dir to exist and not be empty).

## Stances

| # | Stance | Rationale |
| - | ------ | --------- |
| 1 | **Always** use per-child symlinks for `~/.codex/skills`, never a single dir symlink | `.system/` is Codex-managed; a dir symlink pollutes Claude with Codex artifacts |
| 2 | **Never** touch `.system/` - it's regenerated by Codex on startup | Writes there are at best ignored, at worst overwritten |
| 3 | **Always** verify `~/.codex/config.toml` exists before syncing | Detection protects against writing into a stale empty `~/.codex/` |
| 4 | **Prefer** symlinks over copies even for small files like `AGENTS.md` | Edits to the repo guidance file should be instantly visible in Codex - copies defer updates |
| 5 | **Never** store Codex-only config in the shared repo | Things like `config.toml`, `auth.json`, `sessions/` belong only to Codex |
| 6 | **Always** normalize symlink targets - `agents/` with trailing slash and `agents` without are semantically equal but `readlink` reports them differently | First sync normalizes; all later syncs show "skip" instead of "retarget" churn |
| 7 | **Always** project every Claude command as a Codex skill wrapper, never as a standalone file in `~/.codex/` | Codex has no user-command surface; standalone `.md` files in any Codex dir are inert. Wrapping each command as a skill is the only way to make it auto-load by intent. |
| 8 | **Always** symlink hook scripts and translate the repo `settings.json` hooks block into Codex's `hooks.json` — never hand-maintain `~/.codex/hooks/` or `~/.codex/hooks.json` | Real files drift. Symlink scripts plus translated JSON keep Codex aligned with the repo source. |

## Known Codex Quirks

| Quirk | Impact | Mitigation |
| ----- | ------ | ---------- |
| `state_5.sync-conflict-*` SQLite files accumulate under Syncthing | Dozens of MB of dead state; no functional harm | Out of scope for sync engine; clean manually when convenient |
| Codex writes `config.toml` additions (plugin entries, trust_level) mid-session | Not tracked by sync; Codex-owned | Leave alone; sync engine only touches our shared artifacts |
| `.stignore` at `~/.codex/` level | Separate Syncthing folder from `~/.claude` | Both can be synced independently; our symlinks cross folder boundaries but symlinks themselves sync fine |
| A harness's own `AGENTS.md` may hold stale, harness-specific content | Diverges from the source of truth | The sync engine replaces it with a symlink to the config repo's guidance; back up any local copy you want to keep before the first sync |
| 1024-char cap on SKILL.md frontmatter `description` | Skills with longer descriptions are silently skipped at Codex startup with a warning - Claude itself has no such cap, so the skill works there but vanishes from Codex | Keep each skill `description` under 1024 characters (aim for headroom below ~900) so skills load in Codex as well as Claude |
| Codex has no user-command surface | `/<name>` style invocation only resolves to built-in slash commands; no user-defined slash registry | Project commands as skills via `strategy_command_to_codex_skill`. Skills auto-load by intent matching the description triggers. |
| Some commands lean on Claude-only tools (`Skill`, `TaskCreate`, `AskUserQuestion`, `Task` for agent delegation) | When such a wrapper auto-loads in Codex, the model can read the workflow narrative but can't execute the orchestration scaffolding | Acceptable trade-off: the prose still guides the model and the Bash/Read/Write portions do execute inline. Workflows that depend heavily on agent fan-out or interactive choice will surface degraded results - note that in the response. |

## Command Projection

Codex has skills, agents, MCP servers, hooks, and apps as first-class extensions. There is no user-command surface, so every command in the repo `commands/` directory is projected as a skill wrapper at `~/.codex/skills/cmd-<name>/SKILL.md`. The wrapper's frontmatter description includes the original command description plus trigger keywords (the command name, `/<name>`, "run <name>", "do <name>"); the body inlines the command workflow with `$ARGUMENTS` rewritten to a Codex-friendly placeholder.

Skills auto-load when user intent matches their description triggers. Saying "sync harnesses" or typing `/meta-agent-sync` both load the `cmd-meta-agent-sync` wrapper, which then carries the sync workflow into the conversation.

### Degradation awareness

Commands that rely on Claude-only tools (`Skill`, `TaskCreate`/`TaskUpdate`/`TaskList`, `AskUserQuestion`, `Task` for agent delegation) degrade in Codex - the model reads the workflow narrative but cannot execute the orchestration scaffolding. The Bash/Read/Write portions still execute inline; the agent-fan-out and interactive-choice portions become "the model would do X next." This is acceptable for discoverability: the workflow guidance is still present and useful even when partially executable.

Per-command degradation tier (`Bash/IO ÷ (Skill + 2·Task + 3·Ask + 2·Agent)`):

| Tier | Behavior in Codex | Commands |
| ---- | ----------------- | -------- |
| **High** (≥0.70) | Mostly executable; orchestration is light | meta-agent-sync, doc-learn, sde-git, meta-agent-test, doc-domain |
| **Medium** (0.40–0.70) | Body executes; some scaffolding becomes narration | career-hunt, sde-lint, solve-comments, meta-mem-test, sde-monitor, solve-conflicts, doc-arch, meta-agent-learn, doc-structure |
| **Low** (<0.40) | Workflow narrative loads; agent-fan-out and interactive prompts degrade to prose | plan-review, sde-code, sde-test, doc-code-health, sde-review, solve-issue, doc-design, sde-ship, plan-ultrathink |

When invoking a low-tier command in Codex, surface the degradation explicitly so the user knows which portions ran and which were narrated.

### Verification

```bash
ls ~/.codex/skills/cmd-*/SKILL.md # one per command file in the repo commands/
```

In the Codex TUI, mention the command name or type `/<name>` - the wrapper skill loads and the workflow narrative becomes available.

## Codex Config Trust

Codex sessions often need to operate on `~/.claude` (the source of truth) without permission prompts. Grant that by listing your `~/.claude` path under Codex's `projects` trust config in `config.toml`. Codex stores the key as a fully resolved absolute path, so use your real home directory (`/Users/<you>/.claude` on macOS, `/home/<you>/.claude` on Linux, `C:\\Users\\<you>\\.claude` on Windows):

```toml
[projects."/Users/<you>/.claude"]   # replace with your absolute ~/.claude path
trust_level = "trusted"
```

## Anti-Patterns

| Don't | Why | Instead |
| ----- | --- | ------- |
| `ln -s "$HARNESS_CONFIG_REPO/skills" ~/.codex/skills` | Swallows Codex `.system/` into the shared repo | Per-child symlinks with `.system` in preserve list |
| Hand-copy repo hooks into `~/.codex/hooks/` once and forget | Drifts the moment the repo hook is rewritten | Let `strategy_symlink_children` keep them in sync; never replace a symlink with a real file in `~/.codex/hooks/` |
| Hand-maintain `~/.codex/hooks.json` | Same drift risk plus path-prefix bugs | Edit hooks in the repo `settings.json`; the translator updates `~/.codex/hooks.json` on next sync |
| Edit `~/.codex/AGENTS.md` expecting it to stay | It's a symlink to the repo `CLAUDE.md`; edits land there but the file is managed by the repo | Edit the repo `CLAUDE.md` directly |
| Remove the `AGENTS.md` fallback from detection | Pre-config.toml installs stop being detected | Keep both in the OR |
| Sync into a fresh `~/.codex/` that Codex hasn't initialized yet | No `config.toml` yet; detection fails (as intended); but if you bypass, Codex may then reject our files | Run Codex once first to let it initialize |
